# Android WebSocket 心跳与自动重连需求

## 背景

当前 Android 前台聊天界面虽然以 WebSocket 为主要实时链路，但还缺少两项关键能力：

1. 没有应用层心跳，难以及时识别“表面连接存在、实际已失活”的假活连接
2. 没有稳定的自动重连与退避机制，连接断开后恢复依赖较弱

这会导致：

- 前台实时体验不稳定
- 网络抖动后恢复慢
- 需要依赖手动刷新或 HTTP 补偿

## 目标

- 为 Android 前台 WebSocket 增加应用层心跳
- 在连接断开、失败、心跳超时后自动重连
- 使用有上限的退避策略，避免频繁抖动时疯狂重连
- 重连成功后主动补一次 bootstrap，尽快恢复最新会话状态

## 范围

### 本轮纳入

- Android 客户端 WebSocket 周期性发送 `heartbeat`
- hub 对客户端 `heartbeat` 返回确认消息
- Android 客户端维护最近一次入站时间
- 心跳超时后主动关闭当前 socket 并进入自动重连
- 自动重连退避
- 重连成功后自动刷新一次 bootstrap

### 本轮不纳入

- 后台通知链路去轮询化
- 移除前台服务
- 移除 HTTP fallback
- 复杂网络诊断 UI

## 设计判断

### 1. 心跳形式

推荐使用当前协议体系内已有的应用层 `heartbeat` 消息，而不是只依赖底层 TCP / WebSocket ping。

理由：

- 更容易和现有 JSON 协议统一
- 更容易在日志里观察
- 更容易做“服务端确认”

### 2. 重连策略

推荐采用指数退避并设置上限，例如：

- 1s
- 2s
- 4s
- 8s
- 15s 上限

理由：

- 短暂抖动时恢复快
- 持续故障时不会过度打爆 hub

### 3. 前台与后台分工

- 前台实时会话：`WebSocket + 心跳 + 自动重连`
- 后台系统通知：继续保留 `前台服务 + 轮询`

本轮不试图让后台通知完全依赖 WebSocket。

## 验收标准

- Android 前台会定期发送 `heartbeat`
- hub 会返回 `heartbeat_ack`
- 若超过阈值未收到服务端确认或其他入站消息，客户端会主动触发重连
- 断开后会自动重连，不需要用户手动重新连接
- 重连成功后会自动刷新最新消息
- 使用本机 Android 模拟器完成自测，并验证：
  - 心跳存在
  - 断线后能自动恢复
  - 恢复后会话内容同步正常

# Android Agent 系统通知需求

## 背景

当前 Android 客户端已经能实时看到 agent 会话、消息和状态，但当用户不在 App 前台时，仍无法像 IM 一样被动收到 agent 的新消息提醒。

这会削弱“个人私有 Agent IM”的核心价值，尤其是在以下场景中：

- agent 任务完成后回消息
- agent 失败或需要确认
- agent 生成新的结果摘要或图片预览

因此需要为 Android 客户端补充原生系统通知能力。

## 目标

- 当 agent 产生新的有效消息时，Android 客户端通过系统通知提醒用户。
- 通知点击后可直接回到 App 并打开对应会话。
- 在 App 前台已可见当前内容时，避免产生重复打扰。
- 优先使用 Android 官方通知机制，不引入第三方推送服务。

## 范围

### 纳入本轮

- Android 原生通知通道
- Android 13+ 的 `POST_NOTIFICATIONS` 运行时权限请求
- 基于后台轻量轮询的通知触发
- 点击通知后直达对应 agent 会话
- 用于维持后台提醒能力的 Android 前台服务
- 针对以下事件类型的通知：
  - `text_output`
  - `need_approval`
  - `task_failed`
  - `artifact_generated`
  - `image_available`

### 明确不纳入本轮

- 厂商私有推送服务适配
- Android 前台服务常驻通知
- 自定义通知回复输入框
- Xiaomi HyperOS 超级岛专用适配
- iOS 通知实现

## 设计判断

### 1. 何时通知

推荐规则：

- 仅对 agent 发出的“有效会话消息”发通知
- 不对 `user_command`、`agent_started`、`agent_stopped`、`task_running`、`task_completed` 这类过程消息发通知
- App 在前台时默认不发系统通知，避免和当前界面重复

### 2. 通知内容

- 标题：agent 会话名称
- 正文：消息摘要
- 分组键：按 agent 会话分组
- 点击动作：打开 App 并定位到对应会话

### 3. Xiaomi HyperOS / 超级岛

本轮不做厂商私有适配。

工程判断：

- HyperOS 超级岛没有稳定、公开、低维护成本的通用 API
- MVP 阶段不值得为私有 ROM 能力牺牲实现稳定性
- 先把标准高优先级通知做好，交由系统按 ROM 自身策略展示

### 4. 后台可靠性路线

工程判断：

- 在不接入 FCM、第三方 IM、公网推送或系统级中转的前提下，普通前台页面进程无法稳定承担后台实时提醒职责。
- 因此 MVP 采用 `前台服务 + 后台轻量轮询` 的路线维持私网通知能力。
- 这会引入一条常驻系统通知，但能显著提升个人私有 Agent IM 的后台可达性与可靠性。

## 验收标准

- Android 13+ 首次启动时可请求通知权限
- App 成功连接 hub 后，会启动后台通知服务并显示常驻服务通知
- App 在后台时，收到新的 agent 有效消息后会出现系统通知
- 点击通知后可进入对应会话
- 初次连接加载历史消息时不会把旧消息批量误发为通知
- 后台轮询获取到新消息时，也能触发通知
- 使用本机 Android 模拟器完成自测，验证通知出现与点击跳转路径
